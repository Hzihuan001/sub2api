同一请求中同一实际账号、上游模型、平台和端点失败后，备用分组关联同一路径不重复执行；不同映射不得仅因 AccountID 相同被误排除。正常原生同账号重试的每个真实推理尝试可形成独立样本，不与外层终态重复计数。

### 1. 候选、一次失败与长期冷却

每组候选必须是支持当前公开模型及其实际映射、支持请求端点、且通过原生权限/凭证/配额/调度准入的账号。自定义规则只额外排除当前 Key 范围的账号，不更改全局账号状态。

本次请求的失败排除与跨请求累计冷却独立：账号本次明确失败后可以按原生有界策略结束其尝试并选择同组其他账号，不必等它累计到冷却阈值；但不能因它达到阈值就跳过尚健康的同组账号。已发出的每个推理重试都有独立 attempt ID、派发时间和终态，只观察一次；未发包的排队、参数拒绝和凭证刷新不形成样本。

### 2. 预算及最后候选

组内候选穷尽、原生重试预算耗尽、请求总预算耗尽必须区分。总次数和总耗时跨组共享，不能每次换组重置。用户已确认：组内预算先耗尽但尚有未试账号时，只要请求仍可安全重放、存在合法备用且总预算尚有余量，允许进入备用组；不把未尝试账号记失败或冷却，也不得暗中把该情况写成“全组冷却”。总预算耗尽必须退出，不无限回环。

TTFT 只有在其他原生合法候选存在且可安全重放时才允许主动取消当前账号子请求；最后一个合法候选只记录慢样本，不被自定义 TTFT 主动截断。仍服从原生请求截止时间，不承诺无限等待。全部账号已软冷却时不额外发付费探测，也不提前绕过冷却。

### 3. 并发与安全重放的接线标准

在原生真实发包边界创建/派发尝试，响应解析、原始 usage、有效内容及原生结果共用同一个防重放闩。即使未配置 TTFT 也启用此闩。任何已知用量、输出、完整成功、不可逆工具副作用、协议不确定性或客户端取消均禁止自动重放。

旧尝试退出、body/连接按原生规则处理、账号并发槽位和相关预留释放后，才允许启动下一尝试。不能由定时器直接选号、写响应或写账。快失败、慢成功、首内容与取消竞争、usage 与计时器竞争均需测试；成功不得被迟到计时器丢弃。

### 4. Redis 与配置代次闭环

只有自定义健康状态的超时、坏数据、CAS 失败或容量不足允许软降级；原生权限、凭证、配置一致性及数据库错误不能一起吞掉。部分账号状态读取失败时，也不能断言“全组都冷却”。降级不清除本次请求已失败账号集合。

请求冻结 scope/规则/代次，读取规则与代次必须一致；保存、删除、关闭、继承变化及删后重建推进单调代次。写入终态前核验权威代次，不能只依赖曾访问 identity 的 Redis Fence 或缓存；旧请求不得换用新代次补记。组属性变化与认证缓存失效不得导致新旧权限、价格和规则混快照。

不同实例以同站点稳定命名空间共享 Redis，三站隔离；不得拿站点显示名称作为唯一隔离标识。规则状态消失可退化为重新累计，但不能绕过原生限制。灾备导致数据库代次回退时，需明确轮换健康状态 epoch 或只清该独立命名空间，不能清业务余额/用量。

### 5. 容量与健康路径性能

上线前按“活跃 Key × 分组 × 账号 × 模型 × 端点”测算基数，按每个身份的峰值派发量配置去重/窗口容量。当前核心默认容量不是生产容量承诺：每身份 1,024 个去重 ID 与 15 分钟接受期在持续约 1.14 次/秒时即可能触顶；每 Key 256 个 identity 也可能不足，必须压测及调整。

增加批量读取/请求内快照，避免每轮选号对整个账号池逐个 Redis 往返；发包前仅对最终账号重新准入，确保排队期间新冷却能生效。验收应覆盖 Redis 全断/部分失败、热 Key、多实例竞争、全站状态内存及恢复；状态容量耗尽必须可观测，不能把静默规则失效当作正常通过。

### A. 用户可观察行为契约

假设主组有 A/B/C，备用一有 D/E。单个请求的正常路径是“原生选择 A → A 明确失败且安全可重试 → 原生有界重试/换到同组 B/C → 本组合法候选耗尽 → D/E”。新请求从配置的主组重新评估，只跳过本 Key 当前有效冷却；不永久把备用组提升为主组，不跨组来回轮询。

| 场景 | 必须行为 | 不允许的行为 |
| --- | --- | --- |
| A 达规则，B/C 健康 | 当前 Key 跳过 A，仍优先本组 | 因 A 达阈值就跳整个组 |
| A 本次失败但未达累计阈值 | 原生有界重试结束后，本请求排除 A；后续请求按累计状态评估 | 要等累计达阈值才肯结束本次失败遍历 |
| 主组不支持模型 | 直接选支持模型的合法备用组 | 必须先向主组发一次必败请求 |
| 全组无本模型合法候选 | 按配置顺序寻找下一组 | 重新清空排除集，循环回刚失败的账号 |
| 同一账号还在别组，实际模型/平台/上游端点相同 | 本次不借不同分组再次执行已失败路径 | 换个价格组就重复执行相同请求 |
| 某账号仅并发满 | 服从原生排队/等待及其超时策略 | 把正常排队记成账号推理失败或立即停用 |
| 规则关闭或删除 | 新请求不再使用该版本冷却；迟到结果不能复活 | 清除原生凭证、配额、限流保护 |
| 无备用组 | 保留原生行为，不启用会锁死单组 Key 的自定义冷却 | 自定义规则把唯一可用组长期锁死 |
| 全部只有自定义冷却 | 有界返回暂不可用；能确认恢复时间时返回合理 Retry-After | 提前破坏用户冷却、后台付费探活或无限重试 |

“合法候选”必须同时满足账号支持当前模型和端点，以及原生权限、状态、凭证、配额、调度与会话限制。只检查账号数量或分组数量不够。

### B. 唯一身份、唯一样本与模式互斥

1. 健康身份采用稳定站点 UUID、Key ID、组 ID、账号 ID、公开请求模型、公开端点、单调规则代次；不存密钥原文。三站数据库各有独立站点 UUID；克隆数据库作为新站并共享 Redis 前必须重置新站 UUID。
2. 实际派发另冻结实际账号、映射后模型、平台、实际上游端点、attempt UUID 和派发时间，用于跨组重复路径判断。不能使用可变的“最后账号”、错误响应里的 modelName 或未经映射的 requestedModel 代替真实身份。
3. 一次真实推理发包产生一个样本；相同 UUID 重复提交只接受一次。一次 Forward 内实际发三次，正好三个，不被外层终态再加一次。
4. 规则计数使用结构化结果，而非扫描/修改错误日志。上游状态码优先；没有上游状态码时，只采用已证明属于这次上游失败的客户端状态码。没有证据不从报错文字猜 502/504。
5. `503` 可代表服务繁忙/过载；某些平台的过载为 `529`。必须按真实日志状态分别匹配，不把 overload 字符串强行统一成一个码。`502` 与 `503` 独立累计。
6. 同一个 Key 同时只有 `group_v1` 或 `account_v2`；新模式不能运行旧组级计数器或旧组级 TTFT。旧 Key 普通保存保持原模式，显式升级才改义；新建多组 Key 的默认账号模式必须在界面说明。

### C. 规则与时间语义

| 规则 | 样本与边界 |
| --- | --- |
| 状态码窗口 | 同账号、同状态在最近窗口内达到次数；参数页跨规则不允许重复状态码 |
| 连续失败 | 仅真实推理结果；成功结束连续序列；未发包的本地拒绝不占位 |
| 超时 | 最近 N 次有效尝试中的真实超时；本地主动 TTFT 取消不伪装成上游 504 |
| 429 | 最近 N 次有效尝试里的真实上游 429；保留原生 Retry-After/限流保护 |
| SLA | 收满 N 次才评估；严格低于阈值触发，等于阈值不触发 |
| TTFT | 每次真实派发独立计时；慢成功只影响后续选择，不撤销本次成功 |

并发结果按固定终态时间及明确的稳定次序计算，实例时钟需同步。冷却已建立时，不因其他在途成功或失败任意清除/延长；冷却到期开始新窗口，冷却前的迟到样本不得污染新窗口。已通过最终准入或已经发出的并发请求可能继续完成，不能承诺触发瞬间所有在途请求立即停止。

### D. 一次尝试状态机和资源所有权

```text
候选检查 → 原生选号/排队/凭证准备 → 最终准入与版本检查
    → 真实派发（独立 UUID/TTFT）→ 解析/有效内容/usage/终态
    → 原生解析和 body 清理 → 原生槽位/相关预留释放
    → 确认清理完成 → 决定结束、换同组账号或换备用组
```

- timer 只取消对应的上游子请求，不能操作 Gin、抢占选组、扣款或提前释放原生槽位。
- 同一 Forward 内部重试需先完成上一 body 的读取/关闭屏障；跨账号和跨组需等整个 Forward、parser、槽位和相关预留清理完成。
- `Body.Close()` 不等于清理完成：存在阻塞中的 Read、异步 parser 或未释放槽位时不允许下一尝试。
- writer、原始 usage reader、原生 parser 与终态必须引用同一个不可变 attempt。不能让旧 reader 跟随动态 provider 观察到 B 的 guard。
- 选号、auth refresh、签名准备和并发队列不算 TTFT；native 内部签名/Token 修复后的推理重发才算新 attempt。
- TTFT 的合法替代候选在每次真实派发前重查；最后一个合法候选只记录慢结果，不主动取消。候选探测只读，不发请求、不占槽、不扣费。

### E. 常驻的安全重放与账务闩

安全闩与 TTFT 配置分离。未启用 TTFT、仅配置状态码/SLA、或当前处于最后候选，仍必须观察 usage 和不可逆事件。

满足以下任一条件，禁止自动换号/换组重发：客户端已收到有效内容、已知非零 usage、完整成功结果、已启动工具或其他副作用、未知协议/无法判断的成功结果、客户端已取消。未知 2xx、空 204、异常正文或不受支持协议不能被随意归为“安全 5xx”。SSE 心跳、注释、role-only 不算有效内容，但已提交的响应头与客户端协议状态仍须在重放许可中考虑。

取消与首内容、usage、完整成功竞争时，以已经获得的成功/用量/副作用证据否决重放。定时器过期不是丢弃晚到成功的理由。全部安全判断完成且清理屏障确认后，原处理协程才可启动下一尝试。

账务模块不新增扣费/退款/使用记录路径。使用原生的实际组价格、用户专属倍率、Key 限额、用量去重及部分结果结算；异步结算必须冻结实际账号、组和价格上下文，不能读取后来切换后的可变 Key。健康写入失败不阻断原生成功结算，也不能促使相同推理再执行一次。无上游 usage 不等于上游没有费用，主动 TTFT 取消可能产生上游成本。

### F. 不同失败的处理和预算

模型不支持、真实候选耗尽、规则冷却、原生重试额度用完、全请求预算耗尽、权限/参数拒绝及存储/调度异常分别处理。用户请求参数错误、余额/授权不足、客户端主动断开不通过换组规避，也不记账号故障。原生凭证/安全限制仍然优先。

本请求失败排除不依赖 Redis，native 503 清空内部排除集后也必须重新合并；Redis 故障不能把本次已失败账号放回来。原生同账号重试本身仍受原生规则和新的最终准入约束，不能借再次进入 handler 重置重试次数。

全请求共享次数和耗时预算，任何换组不重置。当前代码的 256 次/10 小时仅为开发安全上界，**不是建议用户等待 10 小时或新增 256 次付费重试的生产承诺**；正式上限应结合原生配置、候选规模及合成实测确定并记录。没有预算时不得继续发包。

预算策略已获用户确认：组内原生预算已用完、但还存在未试合法账号时，允许提前进入合法备用组；必须同时满足重放安全和全请求预算。不能冒称“账号已耗尽”，不给未尝试账号记失败/冷却；无合法备用或无总预算则有界结束，不重置次数和耗时。

### G. 存储可靠性、延迟与容量上线门槛

- PostgreSQL 保存配置与单调代次，Redis 仅保存可重建的软健康状态。改/删/关/重加相同规则、换主备和继承设置变化均须推进代次并失效认证缓存；不能使用规则内容 hash 充当代次。
- 组规则修改可能通过触发器同时推进多个相关 Key 的代次；真实 PostgreSQL 下须验证锁等待、并发编辑、认证缓存失效负载及事务回滚，不只测试单行读写。删除最后一个备用组、旧缓存认证和普通保存也须证明完全回到单组原生行为。
- 写结果前和真实派发前核验权威代次；历史结果不重新归属到新版本。DB 权限/配置读失败、代次不一致、预算耗尽为硬错误，不能混在 Redis fail-open 中。
- 仅软健康 Redis 失败可降级为原生调度，同时保留本请求失败排除。对冷却的部分读取失败不可判定“全组冷却”。后台不发额外收费探针。
- 为软健康读写设置独立、短且可验收的耗时上限；不能复用 Redis 默认数秒超时及多次重试，把“降级”变成用户等待。独立子超时与入站客户端取消必须区分；前者可软降级，后者必须停止新请求。
- 候选初扫使用批读和请求内快照；只对最终账号重新准入。避免对整个账号池逐个 Redis 网络往返。代次 SQL 也必须记录每请求次数和耗时，不能只优化 Redis 却留下 O(账号数) 数据库轮询。
- 当前实现 defaults 为每身份 1,024 个去重 ID、15 分钟去重期、每 Key 256 个身份；连续约 1.14 次真实尝试/秒即可触及该身份去重容量。每站点再按 16 个确定性 Redis 桶分配默认 10,000 个 identity 的硬上限（每桶 625）；单桶热点可能略早于精确总上限拒绝新 identity。仅 payload 理论边界 256×128 KiB≈32 MiB/Key，**上述参数仍不能原样视为生产容量已达标。**
- 上线前以实际活跃 Key×组×账号×模型×端点基数及真实峰值尝试率测算；验证有效样本、状态体积、CAS 冲突、Redis 内存和容量错误。必要时压缩/裁剪状态和增加全站上限，不能只无上限增大参数。
- 提供有界、脱敏的服务器日志/计数指标：软降级次数、容量错误、CAS 耗尽、重复样本、旧代次拒绝、路由预算耗尽、清理未确认。指标禁止以 Key、账号或模型原文建立无界标签；无需新增用户记录列或原因页，但不能让规则静默失效无人可知。
- 同站多实例共享稳定 UUID；三站隔离；重启应用不清状态。Redis 数据丢失允许重新累计，不宣传丢数据后仍保持冷却。恢复旧 DB 导致代次回退时需独立 namespace epoch/命名空间处理方案，不清业务 Redis。

### H. 平台覆盖与不扩展范围

按真实推理链路登记，逐项完成 HTTP 和 SSE 的调用数、实际模型、计数、安全闩及账务验证。目录发现、count_tokens、额度/余额查询、凭证刷新、监控不记成本次用户推理样本。图片、批量生图、WebSocket、存储会话/文件/后台任务及存在不可逆服务端工具的路径继续按现有准入走原生行为，不借本轮扩展自动重放。

| 推理适配 | 必须核对的真实边界 |
| --- | --- |
| OpenAI / compatible（含 DeepSeek、Kimi） | 插件和 HTTP transport 合为一个真实尝试边界；实际映射后模型；同账号内部重试 |
| Anthropic 原生/透传/协议转换 | 整流/预算重试、最终 reqModel 或 mappedModel；Messages/Chat/Responses 各入口 |
| Gemini 及兼容转换 | 实际 mappedModel；同一函数中的 countTokens 明确排除 |
| Bedrock | 签名后实际 modelID；签名修复后重新推理为新 attempt |
| Kiro | 最终 payload modelId 及空映射回退；排除额外 websearch 等有副作用路径 |
| Antigravity | 从构建好的请求 body 取实际模型；主循环、fallback、retry 和 credits-overages 真实生成重发全部登记 |
| SystemOne 等其他可达文本路径 | 最终验证的模型、协议与实际发包；不得因文件名/平台名忽略旁路 |

这些 provider seam 部分已接入源码中的真实发送位置（最新进度见顶部复核结论），尚未完成全部接线或进入生产。某条路径没有通过验证时，必须保持现有准入限制或明确拒绝对它启用 account_v2，不能静默绕过安全模块却声称“所有平台支持”。最终发布前支持矩阵须明确，无遗漏的可达已承诺路径才算完成。

### I. 与官方主线的解耦约束

纯核心不依赖 Gin/Ent/Redis；存储、原生调度、真实派发、前端分别通过窄接口连接。业务 handler 只负责创建 scope、提交终态/清理确认和有序协调，不复制整段官方 Forward；不另造负载均衡、模型映射、扣费器或账号状态系统。

维护一份 hook 清单和架构契约：实际生产组合 Wire 必须生成；provider 漏接、双重计数、旧计时器误开、任意写全局暂停字段均有失败测试。新增文件、迁移和测试登记到现有 manifest/contracts，后续官方升级可定位少量接点。不修改已发布 9000–9002 校验值，不修改 Ent 生成文件，不夹带本轮之外的官方版本合并。

前端继续现有主备卡片与规则布局；只有有备用组才显示自动切换。增加必要的账号统计说明与旧模式显式转换，不增加使用记录列、路由原因页或全局账号停止状态。原错误日志保留，仅真实跨组的最后因果错误使用已有“切换备用分组：名称”标签；历史冷却初始跳组不伪造错误。

每条测试保存场景 ID、源码/镜像、配置代次、预期/实际上游派发次序、UUID/样本数、最终组、usage/dedup/余额/Key 配额变化和清理结果。成功证据复用；修复失败只针对受影响范围补验，最终固定候选再跑一轮必要全链路。不得反复完整压测却不形成结论。

必须做的确定性故障注入：

1. A503 达阈值、B 成功；A/B 依次耗尽后才走 D；主组无模型；sticky 指向冷却 A。
2. 同组多账号、跨组共享同账号的相同/不同映射、两个 Key 和三站 ID 相同的隔离。
3. 502/503 分开累计、同账号多次真实重试、重复回调、乱序/并发、SLA 满窗及等于阈值。
4. 规则改/删/关/删后重加、继承变化、旧请求晚到、新模式不复用旧组计数。
5. 首内容/usage/成功与 timer 同步竞争；未启用 TTFT、最后候选、未知 2xx、role/心跳、分片/多行 SSE、工具及过大前奏。
6. 阻塞 Read、并发 Close、清理延迟、解析失败、队列超时、客户端断开；下一次发包前清理屏障可证明完成。
7. Redis 全断/变慢/坏载荷/容量满/CAS 竞争、两个实例与重启；SQL/权限/代次错误不误降级；全冷却/预算耗尽有界退出。
8. 失败后备用成功、部分 usage 后断线、主动取消、健康写入失败及异步结算，按实际组逐笔核对，不只检查 HTTP 200。
9. 迁移 9003/9004 从现存迁移序列执行、旧镜像读写/调用、旧缓存、回退再升级；旧规则语义与启用模型限制的退化明确记录。

性能与长连接只使用合成上游，不产生模型费用：相同资源/相同场景下比较当前稳定版和候选的额外路由耗时、SQL/Redis 调用数、TTFT p50/p95/p99；分级并发至 150，限定持续时间并记录 CPU/内存/连接/槽位回落。安排超过历史 10 分钟断连窗口的 HTTP/SSE 场景，验证取消/换号时资源和账目。禁止无预算长时间压测；本地通过不冒称已证明所有国内公网/CF/外部上游永不超时。未解释的延迟、重复调用、扣费或持续资源增长一律阻断上线。

### K. 发布、回滚和最终“完成”定义

发布前备份三站数据及配置并验证可读，记录当前镜像 digest。只替换应用，保留 DB/Redis/卷/网络/反代。正式镜像拉回本地验证与已验候选一致后，按主站、L1、COS 顺序，每站验证健康、版本、权限、模型目录、主备短请求和 SSE、实际组结算与关键日志。生产收费请求只能用已授权预算，不借验收扩张权限。

失败则停止后续站点，仅回退失败站应用；不通过恢复旧 DB 覆盖新业务来回滚。旧程序不理解 account_v2，因此回退语义不是等价账号路由；需演练先关闭自定义规则/恢复旧模式的明确流程。迁移新增表保留，旧程序启动、基本请求及旧配置编辑均需验证，旧新混跑/重新升级也要覆盖。

只有“源码与测试完整 → 固定 Docker 候选联合验收 → 用户通过 → 正式镜像回拉复验 → 三站逐站生产验收 → 文档与精确清理”全部完成，才可标记整轮完成。交付含提交/标签/digest、平台覆盖表、验收报告、已知边界、回滚命令和保留资源清单。清理只删除准确确认不在用且非回滚所需镜像，不删除业务卷，不清整个 Docker 数据盘。
